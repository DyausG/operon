# F1.2 → F4 frontend contract handoff

**Status:** IMPLEMENTED on the backend branch `v2/f1-2-plant-work`, which is local only and **not yet in the shared baseline** `v2/integration-f1-routing`. Integration is coordinated separately. Until then, code against these contracts with fixtures or mocks, and do not assume they exist on `c2273a1`.

**Labels in this document:**
- **[F1.1]**: already in the shared baseline.
- **[F1.2]**: implemented on the F1.2 branch only.

Nothing here is merely proposed. Every payload sample below was captured from the real engine on the F1.2 branch. Identifiers and timestamps are shortened.

## 1. The one semantic change F4 must handle

**`phase: "OBSERVING"` no longer means "verifying".** A confirmed dispatch moves the case to OBSERVING, but only to wait for work. Observation begins only after an eligible work report. Derive the stage from `lifecycle.phase` **plus** `lifecycle.verification.state`.

| `phase` | `verification.state` | Meaning | Suggested stage (F4 decides wording) | Waiting on |
|---|---|---|---|---|
| READY / EXECUTING | `NOT_STARTED` | dispatch in progress | In work (dispatching) | Dispatch (system) |
| OBSERVING | `AWAITING_WORK` | work order committed; nobody has reported work | In work | Assignee (field) |
| OBSERVING | `WORK_NOT_PERFORMED` | work was declined, or the report does not qualify | In work, needs action | Coordinator (reassign, resume, escalate, cancel) |
| OBSERVING | `COLLECTING` | eligible work reported; fewer than `minimum_scores` post-work scores | Verifying | Verification (system) |
| OBSERVING | `EVALUATING` | enough scores; still inconclusive (at most `maximum_scores`) | Verifying | Verification (system) |
| OBSERVING | `BLOCKED` | pre-version-2 case, or invalid lineage: never evaluated | Exception | Engineer (`allowed_commands`) |
| CLOSED | `VERIFIED_RECOVERY` | verified | Closed | — |
| INVESTIGATING | `NOT_RECOVERED` | outcome recorded; re-investigation | Investigating | Analysis |
| ESCALATED | `REGRESSED` | outcome recorded; escalated | Escalated | Engineer |
| any other phase after a dispatch | `ENDED_WITHOUT_OUTCOME` | the case left OBSERVING (cancel, escalate, resume) without an outcome | — | — |

`verification` always describes the case's **latest confirmed dispatch**. On a later cycle the case can be in READY, EXECUTING, PLANNING or INVESTIGATING again while `verification.state` still shows the previous dispatch's result: `NOT_RECOVERED`, or `ENDED_WITHOUT_OUTCOME` after a resume. `NOT_STARTED` appears only before the first confirmed dispatch.

So key the stage on `phase` first, and use `verification.state` to split OBSERVING and to annotate terminal results. Never infer the phase from `verification.state`.

`status.js` currently maps OBSERVING to VERIFYING by phase alone (`status.js:36`). Once F1.2 is integrated, that label is **inaccurate** for `AWAITING_WORK` and `WORK_NOT_PERFORMED`.

## 2. Projection: `alert.lifecycle` (WebSocket `snapshot` / `alert` / `outcome`) and `GET /api/incidents/{id}`

### 2.1 `lifecycle.verification` [F1.2]

| Field | Type | Meaning |
|---|---|---|
| `state` | enum (§1) | what verification is actually doing |
| `code` | string or null | `AWAITING_WORK`, `WORK_NOT_PERFORMED`, `LEGACY_RECEIPT_BOUND_PLAN`, `LEGACY_NO_WORK_ASSIGNMENT` or `LINEAGE_INVALID` |
| `reason` | string | human-readable, safe to show |
| `policy_version` | string or null | `operon-outcome-2` (work-bound) or `operon-outcome-1` (pre-F1.2 history and legacy BLOCKED) |
| `plan_id`, `outcome_id` | string or null | durable records once they exist |
| `work_assignment_id`, `work_report_id` | string or null | the assignment and the eligible report that opened observation |
| `observation_start` | ISO time or null | first second after the **server-recorded** report time |

| `latest_score_at` | ISO time or null | newest post-work score |
| `stalled` | bool | derived: no new post-work score for 2 minutes. **No automatic transition.** |
| `allowed_commands` | string[] | hints for buttons, not authority; the backend re-validates every command |

### 2.2 `lifecycle.work[]`

The F1.1 fields keep their names. The F1.2 additions:
- `state` gains `DECLINED`;
- new fields:
  - `receipt_id` (the dispatch receipt the assignment belongs to);
  - `current` and `superseded_by` / `supersedes_assignment_id` (reassignment history is kept);
  - `instructions[]`, `window_start`, `window_end`;
  - `declined_at`, `declined_by`, `decline_reason`;
  - `performed_at_claimed` (the reporter's claim, attributed), `asset_intervened`, `completed_instructions`;
  - `provenance` (`SIMULATED` for every report about the simulated plant);
  - `eligible`, `eligibility_reasons`;
  - `ack_due_at` / `ack_overdue`, `report_due_at` / `report_overdue` (derived flags only; no transitions).
- **Changed meaning:** `reported_at` is now the server-recorded report time (the verification boundary). F1.1 used the event time, which differs only by microseconds.

States per assignment:
- `ASSIGNED` → `ACKNOWLEDGED` → `REPORTED` (result `COMPLETED`, `PARTIAL` or `NOT_PERFORMED`);
- `ASSIGNED` → `DECLINED`;
- a `DECLINED` assignment, or a `REPORTED` one with `eligible: false`, can be superseded by `reassign_work`.

`eligibility_reasons` values:
- `NOT_PERFORMED`;
- `NO_PHYSICAL_INTERVENTION` (administrative completion only);
- `ATTESTATION_MISSING` (pre-F1.2 report);
- `PERFORMED_AT_OUT_OF_BOUNDS`;
- `INCOMPLETE_COVERAGE`;
- `NO_COMPLETED_INSTRUCTIONS`;
- `REMAINING_WORK_NOT_STATED`;
- `INVALID_INSTRUCTIONS`.

Sample, a reassignment with history kept:

```json
"work": [
  {"assignment_id": "965d…", "state": "DECLINED", "current": false, "superseded_by": "3346…", "decline_reason": "No safe access"},
  {"assignment_id": "3346…", "state": "ASSIGNED", "current": true, "supersedes_assignment_id": "965d…",
   "assignee": {"kind": "WORKER", "reference": "TECH-201", "reference_system": "operon.local.technician_roster"}}
]
```

### 2.3 `lifecycle.plant` [F1.2]: simulated plant facts, never evidence

```json
"plant": {
  "actuator": "simulator",
  "actuations": [{"report_id": "afec…", "status": "APPLIED", "cause": "WORK_PERFORMED", "actuator_kind": "simulator",
                  "work_result": "COMPLETED", "response_profile": "RECOVERS", "mode_before": "arrested",
                  "mode_after": "recovering", "provenance": "SIMULATED",
                  "reason": "simulated plant response to eligible COMPLETED work report afec…: scenario profile RECOVERS"}],
  "pending_report_ids": [], "failures": []
}
```

- **Reported work** (`work[]`) is a claim made by people.
- **A plant actuation** is what the sandbox simulator did in response to that claim.
- **Neither of them is recovery.**

`actuator: "none"` means production: `status` is always `NOT_SUPPORTED` and nothing was applied. `failures[]` lists actuator errors still pending replay. Show this block as sandbox truth labelling, never as "work done" or "recovered".

`plant.actuator` is filled in the WebSocket `alert.lifecycle` and in `GET /api/incidents/{id}`. The `incident` projection embedded in HTTP command responses (§3) carries `actuator: null`, because it is built without the engine's actuator; its `actuations[]` are the same. Read the actuator kind from the alert or the GET.

### 2.4 `lifecycle.read_model` additions [F1.2]

These are full artifact dumps, for the inspector:
- `work_assignments[]`
- `work_reports[]`
- `plant_actuations[]`

### 2.5 Unchanged

`lifecycle.phase` values; `outcome_result`, `plan_id`, `outcome_id`. Note that `plan_id` is null until an eligible report exists. `reconciliation_required` is now also `true` for BLOCKED pre-version-2 cases.

## 3. Commands

All routes return `{ok, command, replayed, result_id, incident: <projection>}` [F1.1 shape, plus `replayed` in F1.2]. A refusal returns `{ok: false, error, incident}`.

| Endpoint | Body | Gate | Errors | Status |
|---|---|---|---|---|
| `POST /api/incidents/{id}/work/{assignment_id}/acknowledge` | `actor_id`, `actor_role?`, `expected_revision`, `note?`, `request_key?` | sandbox (or the legacy trusted flag outside production) | 403 gate or production; 409 stale revision, wrong state, superseded assignment, case not OBSERVING | [F1.1]; `request_key` [F1.2] |
| `POST /api/incidents/{id}/work/{assignment_id}/decline` | `actor_id`, `actor_role?`, `expected_revision`, `reason`, `request_key?` | sandbox (or the legacy trusted flag outside production) | as above; acknowledged work must be reported NOT_PERFORMED instead | [F1.2] |
| `POST /api/incidents/{id}/work/{assignment_id}/response` | `actor_id`, `actor_role?`, `expected_revision`, `result`, `summary`, `findings[]`, `performed_at?` (timezone-aware ISO time), **`asset_intervened`**, `completed_instructions?`, `request_key?` | sandbox (or the legacy trusted flag outside production) | 409 with the reason for malformed or contradictory reports (nothing written); 422 for unknown fields (the caller cannot set provenance) | [F1.1], hardened in [F1.2] |
| `POST /api/incidents/{id}/commands/reassign_work` | `actor_id`, `actor_role?`, `expected_revision`, `rationale`, `assignment_id`, `assignee_reference?`, `request_key?` | commands (not sandbox-gated, like `retry_execution`) | 403 production; 409 unless the current work was declined or reported ineligible | [F1.2] |
| `POST /api/incidents/{id}/commands/resume` | unchanged | — | from OBSERVING only for `WORK_NOT_PERFORMED` or `BLOCKED` (legacy) | [F1.1]; OBSERVING branch [F1.2] |
| `POST /api/incidents/{id}/commands/{cancel,escalate}` | unchanged | — | the audit payload now records open work and "work orders not recalled" | [F1.1] |
| `POST /api/incidents/{id}/outcome` | none | — | `verification.disposition` may be `AWAITING_WORK` or `BLOCKED` | [F1.2] values |

**Report rules** (`operon-work-eligibility-1`):
- **COMPLETED/PARTIAL must send `asset_intervened`.**
- COMPLETED covers every instruction; omitting `completed_instructions` means all.
- PARTIAL needs `completed_instructions` (non-empty) **and** `findings` (the remaining work).
- NOT_PERFORMED must not send `performed_at`, `asset_intervened: true` or instructions.
- `performed_at` must be no earlier than the dispatch and no later than server time plus 60 s.
- Only one report per assignment.
- `asset_intervened: false` is recorded but ineligible (administrative completion).

**Retries:** send the same `request_key` with the same body. The reply is `200` with `replayed: true` and nothing is written twice. The same key with a different body is refused with 409.

## 5. Business summary (`business`) [F1.2]

`events_prevented` and `recovered_value` (and `net_value` and `fleet_projection`, which derive from them) count **only verified recovery**. A dispatch adds nothing to them.

New fields:
- `events_dispatched`
- `events_awaiting_verification`
- `value_basis: "VERIFIED_OUTCOMES_ONLY"`

After a verified outcome, `alert.result` has `recovery_verified: true`, the Outcome's own `recovered_value`, and `value_basis: "ESTIMATED_AVOIDED_LOSS_OF_VERIFIED_OUTCOME"`.

V2 does not render `business`. The legacy KPI deck now shows smaller, truthful numbers.

## 7. Fixtures and frontend tests: expected changes when F4 regenerates against F1.2

- `make_fixtures.py` `SETTLED` records the OBSERVING frame once `observation_plans` exists. That is now **after** the crew's report, so:
  - the OBSERVING frame shows `work[0].state == "REPORTED"`;
  - the CLOSED frame shows `"REPORTED"` with `eligible: true`, plus a `plant_actuations` entry.
- `f1.test.jsx:75-81` asserts `ASSIGNED` and no `WORK_REPORTED` at OBSERVING. That stops holding after regeneration. To keep an `AWAITING_WORK` frame, capture one right after approval, before the crew acts.
- `status.test.js:18-19,27`: the phase-only expectations hold until `status.js` adopts §1.
- No backend change requires editing the committed fixtures. They remain valid F1.1 data, and the F4 tests pass unchanged against them.
- **Verified:** `make_fixtures.py --out <scratch>` against F1.2 produces the approved sequence and passes the generator's own contract checks. The resulting frames are:
  - `observing`: OBSERVING, `COLLECTING`, `[REPORTED, eligible]`, one actuation;
  - `complete`: CLOSED, `VERIFIED_RECOVERY`.
- **Pre-existing generator race, not F1.2:** the `capture()` loop polls every 5 ms while the Guided Demo controller polls every 100 ms. When the controller's timer fires first after the admission tick, the transient `investigating` frame is missed and the sequence check fails.
  - Baseline `c2273a1`: 1 of 6 runs failed this way.
  - F1.2: 1 of 4 runs.
  - A deterministic fix belongs to F4 (`frontend/test/make_fixtures.py`). For example, record `investigating` from the durable phase rather than the polled status, or retry the capture.

## 8. Safety notes for UI copy

- Never present `REPORTED`, `eligible` or `plant.actuations[].status = "APPLIED"` as recovery. Only `verification.state = VERIFIED_RECOVERY` (with `phase: "CLOSED"`) is verified recovery.
- Actor labels come from the backend (`label`), for example "Scenario driver (simulated)" or "Declared identity (unauthenticated)". Show them; no actor is authenticated before F3.
- `provenance: SIMULATED` marks every report and every actuation about the simulated plant.
