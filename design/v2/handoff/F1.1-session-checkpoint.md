### 0.4 Limitations and deferred work (not completed F1.1 capability)

1. **PRISM-initiated runs bypass the technical retry budget.** A technical failure in a PRISM-initiated run is recorded as `NOT_APPLIED`. It does not consume the lifecycle technical retry budget, so it cannot by itself trigger the analysis suspension that `LifecycleService.diagnose` applies. Suspension after repeated technical failure is therefore guaranteed only for the lifecycle's own analysis path, not for every entry point. Unifying the budget across entry points is deferred (PRISM is slated for isolation in a later F1 slice).
2. **Production deployment blocker.**
   - **What is refused in production:** production refuses every human action:
     - approval, rejection and the recovery commands;
     - technical and resource confirmations, and drafts;
     - work acknowledgement and work reports;
     - the Guided Demo.
   - **Why:** the server assigns actor kinds and refuses in production; `authorize` refuses SANDBOX, DECLARED and SCENARIO actors on production incidents; `ActorRef.authenticated` is fixed to False; the legacy trusted-submissions flag never applies in production.
   - **No legitimate user is blocked:** no authenticated production users exist, because human authentication is not implemented. Production can therefore take no human decision until F3 adds an authenticated actor kind admitted in production.
   - **Endpoints with no actor check in any environment:**

     - the provider and PRISM routes.

**Product-owner decisions, final for F1:**
- **2A Hypothesis identity.** Hypotheses have durable IDs that survive across runs.
- **2B Missing-ID fallback.**
  1. A missing reference is a contract problem first, handled by bounded retry.
  2. After that, a deterministic fallback applies only when there is exactly one structurally valid candidate, and it is recorded.
  3. Ambiguity blocks.
  4. There is never fuzzy or prose matching.
- **2C Typed uncertainty.** Severities are MINOR, MATERIAL and BLOCKING.
  - A critic may raise severity, never lower it. Provenance is preserved.
  - MATERIAL uncertainty stays visible to the approver.
  - BLOCKING uncertainty prevents promotion.
  - No confidence percentages are invented.
- **2E Classification.** Failures are classed as TECHNICAL, EVIDENCE, GOVERNANCE, OPERATIONAL or true ESCALATION.
- **2F Retries.** 3 total technical attempts, configurable. A technical failure never creates a permanent escalation.
- **2G Reject.** REJECT returns the case to PLANNING by default and preserves actor, reason and binding.
- **2H Commands.** resume/retry, cancel (CANCELLED becomes reachable and releases admission), retry-execution, and renew approval after expiry. Every command validates state, is auditable and refuses invalid use.
- **2I Planner.** The planner stays inside the diagnosis run.
- **§3 Work.** WORK_ASSIGNED, WORK_ACKNOWLEDGED and WORK_REPORTED are durable facts. Prefer events over phases.
  - Dispatch is not work, work is not recovery, and recovery is not verification.
  - The PlantActuator and simulator refactor is F1.2.
- **§4 Assignees.** An assignee is not necessarily an OPERON user.
- **§5 Environment.** `OPERON_ENVIRONMENT=sandbox` is explicit. The sandbox actor is clearly labelled and never authenticated. Production does not accept sandbox commands.
- **§6 Economics.** Seam only: no tables, no value-at-risk truth.
- **§7 Strands.** Keep Strands and its topology.
- **§11 Frontend.** Change it only where a label became actively false.

## 5. Known issues and debts (deliberately deferred unless noted)

- **Dispatch still drives the simulator.** `engine.execute` still calls `sim.respond_to_intervention` on dispatch, and outcome verification still starts at the receipt. The contracts do not encode "dispatch equals recovery", but runtime behaviour still does until **F1.2** (PlantActuator, verification waiting for WorkReport). The work facts are recorded but not yet consulted by verification.
- **No AWAITING_WORK phase.** `incident.phase` has a SQL CHECK constraint (`001_operon.sql`), so a new phase would need a table rebuild and therefore a migration. The work state is derived from events and projected instead (`work[].state`: ASSIGNED, ACKNOWLEDGED, REPORTED). Report this as the persistence decision; no migration was needed for any F1.1 item.
- **Fallback definition** (product-owner rule 2B, implemented): the structural candidate set is current durable references that (a) have a trusted confirmation in the run's packet and (b) are not claimed by any other suggestion in the report. The fallback is attempted only on the attempt that would spend the budget, after at least one prior HYPOTHESIS_REF_MISSING retry. With a budget of 1 it never applies.
- **Classification choices to report:**
  - A model-declared BLOCKED is EVIDENCE (the case parks).
  - Any non-evidence application-gate refusal is now a TECHNICAL retry. It was ESCALATED before. After the budget is spent it becomes a suspension, which needs a human resume.
  - Run-start failures (preflight) are reported as RETRY and are **not** counted toward the budget (unchanged behaviour).
- **Cancel releases the engine's analysis hold** on the simulated asset ("arrested" goes back to the profile mode). A persisting simulated condition is therefore detected as a new case.
- **Lowering severity is invalid.** A critic `uncertainty_review` that lowers severity raises `InvalidReference` in assessment validation, so the specialist invocation fails and that counts as a technical retry.
- **Production has no admissible human actor until F3.** This is by design.
